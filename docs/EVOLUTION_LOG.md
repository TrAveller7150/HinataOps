# HinataOps 演进日志

本文件记录后续架构和实现改进的背景、方法、验证结果与残余边界；它不同于单次运行的
`docs/evaluations/` 测试记录，关注“为什么改变系统”。

## E-001：Tool 超时可观测性与 Prometheus 子超时

### 原因

受控故障注入期间，Docker 与 Prometheus Tool 曾同时返回笼统的 `target_unavailable`。MCP Server 日志
显示真实原因是 `SSH command timed out`，但原始错误契约无法区分命令超时、远端命令失败和输出超限。
Prometheus Tool 在一条 SSH 会话中串行执行七个 `curl` 查询，单条请求没有独立超时，可能耗尽整体预算。

### 方法

- 将 SSH 失败细分为 `ssh_command_timeout`、`remote_command_failed` 与
  `output_budget_exceeded`，对外保持脱敏消息并明确可否重试。
- 为每条固定 Prometheus `curl` 增加 1 秒连接超时与 1.5 秒总时限，确保七条查询不会由单条卡顿占满
  15 秒 Tool 预算。
- 保留 Docker 全量快照：恢复后实测其耗时仅 0.388 秒、输出约 95 KB，当前缺少证据证明它是稳定瓶颈。

### 结果

Tool 错误现在能把“瞬时 SSH 命令超时”准确传递给 Agent 的受控重试机制；Prometheus 查询拥有明确的
子级超时边界。Docker 全量快照的裁剪暂不实施。

### 验证与边界

本轮以单元测试验证错误映射和 Prometheus 命令参数；真实受控故障场景尚需在后续运行中验证新的
`ssh_command_timeout` 分类与重试记录。单条 Prometheus 查询超时后，现有固定响应解析会把该 Tool 降级
为部分证据，而不会伪造缺失指标为健康状态。

已在当前 `aoi-local` 环境进行一次只读真实验证：新命令可在 `0.919s` 内完整解析两个 Judge Worker 的
7 条 Prometheus 响应。初次原始命令采样曾耗时约 5 秒，但未超过 15 秒总预算；仍需在后续多次采样中记录
延迟分布，而不能据此宣称瞬时超时已被消除。

## E-002：单窗口人工调查 CLI 与可读过程输出

### 原因

此前真实评测要求用户在一个终端手动启动 Streamable HTTP MCP Server，再在另一个终端运行
`evaluation_runner`；后者把完整 JSON 直接打印到控制台。前者增加了启动步骤，后者把用于归档、评测的
机器格式误当成面向运维人员的交互界面。

### 方法

- 新增 `hinataops investigate python-judge-worker-unavailable`。未指定 `--mcp-url` 时，它在当前 Python
  环境启动本地 MCP 子进程，以实际 `list_tools` 成功作为就绪条件，并在任何退出路径回收该子进程。
- 若用户显式提供 `--mcp-url`，CLI 只连接已有 Server，绝不终止其生命周期，保留开发调试与未来远端部署
  的入口。
- 为 Investigation Workflow 增加仅通知的事件出口。展示层可接收 Tool Catalog、计划采证、开始采证、
  单项观测完成和诊断阶段事件；监听器异常被隔离，不能改变 Planner、预算或 Tool 执行。
- 使用 Rich 渲染中文进度与最终报告；完整 JSON 默认以 UTF-8 写入 `.hinataops/runs/`，而不是输出到终端。
  `evaluation_runner` 保持原有 JSON 基线用途不变。

### 结果

人工调查由两个窗口和冗长 JSON 收敛为一条命令、过程进度和一份可定位的审计记录。MCP 仍是独立 HTTP
信任边界，因此将来 FastAPI/SSE 展示层可以复用相同 Agent Core 与 MCP Server，而无需改写 Tool 层。

### 验证与边界

新增 CLI 参数、默认归档路径和工作流事件隔离测试；全量测试为 65 项通过。本地冒烟检查已确认
“启动 MCP → `list_tools` 就绪 → 退出回收”可用，未调用 LLM 或远程基础设施。当前人工命令仅开放已有
真实基线的 Python Judge Worker 场景；它尚不是可自由输入任意事故描述的通用对话 CLI，也没有实时取消、
历史检索或人工审批操作入口。

## E-003：评测 Ground Truth 与人工调查解耦

### 原因

首次人工 CLI 直接复用了 `python_judge_worker_unavailable` 评测场景。尽管 Planner 只收到事故描述，
诊断器仍收到该场景的唯一允许根因码。这把评测期望答案带入了人工调查，且场景名容易让使用者误以为
Agent 已预设“Worker 不可用”。同时，CLI 仅显示 Core 生成的通用 `complete` 摘要，隐藏了 Prometheus、
Docker 和 Redis 观测中的实际指标与模型候选假设。

### 方法

- 新增不含 Ground Truth 的 `python_judge_task_no_result` 事故画像；每次运行生成新的 Incident ID。人工
  CLI 只使用事故描述、只读 Tool 白名单与预算，诊断器不再接收预期根因码。
- 保留 `EvaluationScenario` 与 `evaluation_runner` 原有逻辑：仅评测入口把 expected cause code 作为
  评分约束传入，评测与人工审计记录分离。
- 在 AoiLearn Plugin 新增 Evidence Presenter，将领域结构化数据压缩为有界关键指标：Worker 可达性和
  沙箱池、Judge 容器状态、Redis consumers/lag/pending 及流水线聚合。Agent Core 仍只产出通用 Observation。
- CLI 新增“模型假设评估”面板，显示候选/主根因、置信度、支持与反驳证据、待补充事实；并把预算耗尽
  明确标成“预算受限结束”。人工画像的 Tool 预算从 4 调整为 5，使四次采证后模型能主动结束。

### 结果

健康环境中的人工调查现在应明确显示“Worker 不可用”只是被证据反驳的低置信候选，而不是预设或确认的
根因；过程输出也会展示实际指标。评测仍可验证受控故障注入时是否命中 `judge_worker_unavailable`，但该
答案不会进入人工调查 Prompt 或归档 JSON。

### 验证与边界

新增领域展示器、人工归档不含 `evaluation`/`expected_primary_cause_code`、候选假设渲染等测试；全量测试
为 69 项通过，并完成 CLI 帮助命令与 Python 编译检查。尚未用本轮代码发起真实 LLM 调查，避免未经用户
确认消耗 API 额度；下一步应在健康负例和受控 Worker 停止正例各运行一次，观察模型是否主动结束及指标
展示是否足以让人工复核。

## E-004：可审计调查决策轨迹与分批采证

### 原因

人工 CLI 虽已展示 Tool 结果，但只能看到“计划采证”和最终报告，无法判断模型为什么选择某项检查、是否在
新证据出现后改变路径，或为什么停止。一次真实运行还出现 `LLM 返回内容不是 JSON`：错误仅在最终停止原因
中可见，难以定位是 Planner 契约失败还是基础设施观测失败。

### 方法

- 定义 `PlanningTrace`：每轮保存状态（已规划/主动结束/规划失败）、受限决策摘要、至多两个 Tool 调用与
  结束原因。它保存的是模型面向人工的简短决策摘要，不是不可审计的内部思维链。
- Planner 的结构化契约新增必填 `decision_summary`，要求陈述已知事实、仍缺证据与本轮选择原因；每轮最多
  两项 Tool，使下一轮确实能使用上一批观测，而非一次并发穷举全部检查。
- 规划失败立即发布事件并写入运行记录，再降级为基于现有证据的诊断；终端最终显示完整“调查决策轨迹”。
- 对 JSON Object 模式返回的单层 Markdown JSON 代码围栏进行严格剥离后再 `json.loads`，兼容供应商偶发的
  围栏包装；其他非 JSON 内容仍按契约失败处理，不做猜测性修复。

### 结果

终端现在可按轮次阅读“模型决策摘要 → 受控采证 → 新观测 → 下一轮决策”，归档 JSON 同时保留该轨迹。
如果 Planner 再次产生无效结构化输出，用户会在发生时看到明确的 `规划失败`，并能从运行记录区分其与
MCP Tool 超时、部分证据或诊断器失败。

### 验证与边界

新增 PlanningTrace、Planner 输出契约、规划失败降级和 Markdown 围栏 JSON 兼容测试；全量测试为 70 项通过，
并完成编译与 CLI 帮助检查。尚未运行真实 LLM，以免擅自消耗 API 额度。该轨迹是模型受 Schema 约束生成的
可审计摘要，不应被当作模型全部内部推理或绝对可信事实；事实仍以 Observation 与其来源 Tool 为准。

## E-005：预算与诊断降级可见性校准

### 原因

健康负例的新版 CLI 显示三轮合理决策：先检查 Worker/队列，再检查流水线/容器，最后计划扩大 MySQL
窗口并使用 SQL 通道对照。但人工画像仅允许 5 次 Tool、3 轮，前两轮已用 4 次，第三轮提出两项检查后被
预算原子拒绝。最终诊断模型又发生结构化输出失败，系统正确降级，却只显示“未形成可确认根因”，使预算
不足与诊断失败混在一起，容易被误判为 Agent 没有分析过程。

### 方法

- AoiLearn 人工画像调整为最多 7 次 Tool、4 轮：支持三轮各两项分批采证，并保留第四轮根据完整证据主动
  结束或补充一项检查的空间。
- Planning Context 新增 `remaining_tool_calls`，系统提示明确要求模型不得超出剩余额度；保留策略层的
  原子授权，避免为了凑预算而静默丢弃同批 Tool。
- 诊断器失败会即时发布 `diagnosis_failed` 事件，并以脱敏的失败类别写入报告与审计 JSON。Pydantic 的
  完整异常输入不再回显，避免把完整模型上下文输出到 CLI。

### 结果

预算限制现在对 Planner 可见，且人工可在终端区分“证据不足”“预算受限”“规划输出失败”和“诊断输出
失败”。此前运行中第三轮尚未执行的 MySQL 60 分钟窗口与 SQL 对照检查，在下一次健康负例中可获得执行机会。

### 验证与边界

全量测试为 70 项通过，Python 编译与 diff 检查通过。尚未运行真实 LLM 回归，因此不能假定提高预算会自动
产生确定根因：当前事故入口缺少具体任务 ID、提交时间与用户上下文，健康环境下仍可能正确输出
`inconclusive`；本轮目标是获得完整、可解释的调查和明确的降级原因。

## E-006：受限的模型格式兼容与 JSON 自修复

### 原因

一次健康负例中，Planner 前三轮均成功给出合理的分批采证决策，但第四轮返回了
`decision_summary_note`，而契约只允许 `decision_summary`。由于 Pydantic 配置为
`extra="forbid"`，这个不参与 Tool 执行的说明字段触发 `extra_forbidden`，使该轮被整体拒绝。
同次运行中诊断器还返回了非 JSON 内容；旧实现没有重试，也没有在脱敏前提下区分这类格式失败。

这说明问题既来自模型供应商的 Schema 漂移，也来自客户端把“非执行展示字段”与 Tool 名称、参数、结束码
同等严格处理。前三轮成功的事实也表明这不是 Planner 持续不可用或调查逻辑整体失效。

### 方法

- Planner 只对已知别名 `decision_summary_note` 做兼容：若缺少 `decision_summary`，将其作为审计摘要恢复；
  若同时存在，则丢弃该重复说明字段，并在 `PlanningTrace.compatibility_note` 记录。未知字段仍由
  `extra="forbid"` 拒绝，Tool 名称、参数 JSON 与结束码没有放宽。
- OpenAI 兼容传输层对“空内容”或“无法解析为 JSON”的响应额外请求一次，并在第二次系统提示中明确要求只返回
  一个 JSON 对象。第二次仍失败时只记录响应字符数和失败类别，不回显模型原文或可能包含上下文的数据。
- CLI 与归档沿用原有调查决策轨迹，额外显示“格式兼容”说明；诊断失败仍会显示明确的降级原因。

### 结果

已知的 DeepSeek 非执行字段漂移不再中断已经正确推进的调查；真正未知的模型输出仍会停止 Planner，保持
只读调查的安全边界。诊断器偶发的非 JSON 返回有一次恢复机会，失败时也能区分为模型格式问题而非 Tool
观测问题。

### 验证与边界

新增 4 个回归测试，覆盖非 JSON 后重试成功、失败不泄露原文、已知别名兼容，以及未知字段继续拒绝；全量
测试为 74 项通过，并完成 Python 编译与 diff 检查。尚未执行真实 LLM 回归，因此下一次应运行健康负例并
检查：若出现 `decision_summary_note`，终端轨迹会标记格式兼容；若诊断器首次输出非 JSON，则观察第二次是否
恢复。一次重试只处理格式瞬态，不能替代模型质量评测，也不应无限重试。

## E-007：统一结构化输出兼容通道

### 原因

E-006 仅对 Planner 的一个已知字段做兼容，仍然把“如何请求 JSON”“如何解析 JSON”“何时因字段或业务语义
失败而修复”分散在传输层、Planner 和 Diagnostician 中。实测中格式问题占比很高时，这种逐字段修补无法支撑
不同厂商、不同能力等级模型的稳定接入。

### 方法

- 建立 `StructuredOutputClient.create_validated_json`：由同一通道完成供应商请求、确定性 JSON 解析、调用方传入的
  严格校验函数及最多两次总尝试。Planner 和 Diagnostician 都通过它运行。
- OpenAI-compatible Adapter 增加三种能力模式：`json_schema`、`json_object`、`prompted_json`。最后一种不发送
  `response_format`，用于兼容会拒绝该 API 参数的模型服务。
- 语义校验也进入修复回路：Planner 的 Tool 白名单与参数、Diagnostician 的根因码和证据引用，均不能通过一次
  “看起来是 JSON”的输出绕过。修复提示只包含字段位置或安全的语义原因，不带模型原文。
- 解析规则扩展为纯 JSON、单层围栏、正文中唯一 JSON 对象；多个候选仍失败，避免从不可信自然语言中猜测执行数据。

### 结果

格式兼容从领域逻辑中退出，成为可替换 LLM Adapter 的通用能力。新供应商先选择其能力模式；若协议完全不同，
实现同一 `StructuredOutputClient` 端口即可，Agent Core 无需理解供应商 SDK。严格 Pydantic 与业务授权仍是
执行前最后一道边界。

### 验证与边界

新增语义校验失败后重试、`prompted_json` 不发送 `response_format`、通用供应商配置的测试；全量测试为 77 项
通过，并完成 Python 编译与 diff 检查。CLI 与评测已从 `llm.local.toml` 读取模型、地址和能力模式，同时兼容
既有 `[deepseek]` 密钥文件。尚未用真实 DeepSeek 执行，避免擅自消耗 API 额度。该机制提高“拿到可验证 JSON”
的成功率，但不提高错误根因的真实性；模型质量、提示词、Tool 覆盖度仍须由健康负例与受控正例评测衡量。

## E-008：空模型响应的安全诊断元数据

### 原因

健康负例 V5 中 Planner 已连续四轮完成采证和主动结束，但 Diagnostician 两次返回空 `content`。原有错误只显示
“无法唯一提取 JSON 对象（响应字符数=0）”，无法判断模型是否因长度截断、推理字段与正文分离，或供应商瞬时
返回空结果而失败。

### 方法

- 将 `None` 内容与空字符串内容显式分类为“未返回结构化内容”和“返回空内容”，不再让空字符串落入通用 JSON
  解析错误。
- 对每个失败尝试记录并在最终降级原因中汇总：轮次、内容状态、标准化 `finish_reason` 与
  `reasoning_content` 是否存在。只接受标准停止码，其余统一为 `unknown`。
- 不记录模型响应、推理正文、Prompt 或密钥；测试以虚构推理文本确认错误字符串不会包含该文本。

### 结果

下一次真实调查若再次出现诊断空响应，将可直接看到它是否带 `finish_reason=length` 以及是否存在推理字段，
从而决定后续应调整输出预算/供应商能力 Adapter，还是按服务瞬态失败处理。

### 验证与边界

新增空内容双重失败、元数据汇总和推理文本不泄露的测试；全量测试为 78 项通过，并完成 Python 编译与 diff
检查。元数据只能帮助定位响应形态，不能读取或恢复被供应商隐藏的推理内容，也不能证明具体供应商的内部原因。

## E-009：诊断输出预算与根对象修复约束

### 原因

V6 安全元数据显示，Diagnostician 的第一次响应为 `finish_reason=length` 且存在推理字段，证明此前的 2000
输出 token 预算不足以同时容纳模型推理和嵌套诊断 JSON。第二次修复虽生成了 JSON，却把候选根因字段放在根
对象，缺少 `status`、`hypotheses`、`conclusion` 等报告顶层字段。

### 方法

- `max_tokens` 下沉为 LLM 连接配置，默认与旧 `[deepseek]` 兼容配置均设为 8192；CLI 和评测通过同一个配置
  构建 Client，不再各自隐含 2000 的默认预算。
- 每次结构化修复都从当前 JSON Schema 提取顶层必填字段，明确要求返回完整根对象，禁止只返回嵌套对象、候选
  根因或字段片段。该规则是通用的，不把诊断字段硬编码进传输层。

### 结果

下一次诊断请求拥有更充足的生成空间，且当第一次输出被截断或字段不合法时，第二次请求会明确给出完整顶层
结构要求。系统仍拒绝本地“补齐”单个候选根因，避免将模型不完整输出伪造成可执行诊断报告。

### 验证与边界

新增 `max_tokens` 配置读取与动态顶层字段修复提示断言；全量测试为 78 项通过，并完成 Python 编译与 diff
检查。8192 是当前实验预算而非所有供应商的最佳值，真实运行后仍需根据 `finish_reason`、成本和稳定性调整；
若足额预算后仍频繁产生错误根对象，再考虑拆分或简化诊断契约。

## E-010：诊断确认门槛、采证收尾轮与 CLI 折行

### 原因

V7 首次成功生成完整诊断报告，但主假设置信度仅为 45%，且缺少 task_id、提交时间、任务级数据库记录与日志；
模型却声明 `diagnosed`。同次调查共执行四批采证、仅使用六次 Tool，却因 `max_rounds=4` 无法进入第五次 Planner
调用来主动结束。终端表格还因“完整记录”路径不可拆分，压缩了结论和决策轨迹中的长文本并显示 `…`。

### 方法

- Diagnostician 提示词明确确认阈值为 70%。Core 在构造报告时再次执行该策略：低于阈值的模型主假设保留为候选，
  取消 `primary_hypothesis_id`，将状态和结论确定性降为 `inconclusive`，不依赖模型自行遵守。
- 将 `max_rounds` 明确为采证批次上限。第四批采证后 Planner 可获得一次 `remaining_tool_calls=0`、
  `remaining_evidence_rounds=0` 的收尾机会；策略层仍禁止第五批 Tool 调用。
- 报告摘要从二维 `Table.grid` 改为可自动换行的文本组；决策轨迹和假设表的长列明确使用 `overflow="fold"`。

### 结果

Agent 不会把低置信、间接证据驱动的猜测展示为确定根因，同时仍能向用户提供候选与人工核查路径。调查停止原因可
区分真正的模型主动结束和预算截断；窄终端也会保留完整结论和路径文本。

### 验证与边界

新增低置信状态降级、四批采证后收尾决策和 80 列终端长文本折行测试；全量测试为 81 项通过，并完成 Python
编译与 diff 检查。70% 是当前 Demo 的保守策略值，不等于统计置信区间；当增加任务级关联证据和更多评测场景后，
应根据误诊/漏诊结果重新校准，而非永久固定该阈值。

## E-011：从场景 Demo 转向生产级通用 SRE 调查平台

### 原因

早期文档把 HinataOps 定位为围绕 AoiLearn 的“可扩展运维 Agent Demo”，并把 API、持久化上下文、通用探索
Toolset 等能力列为非目标。这符合最初控制范围、尽快完成真实闭环的需要，却容易让当前实验环境反向决定长期
架构，使项目不断修补单一场景，而没有形成可迁移的 SRE 调查平台能力。

“Demo”描述的是当前实现成熟度和可用环境有限，不应成为目标架构的上限。最终方向调整为与 HolmesGPT 同类的
生产级通用 SRE 调查平台：支持异构事故入口、可插拔 Toolset、跨数据源调查、证据溯源、上下文治理、持久化
执行、人工审批处置、平台可观测性和持续评测。AoiLearn 改为首个参考集成、故障实验环境与端到端验收场。

### 方法

- 将文档明确拆分为“最终产品目标”“当前 V2 实现”和“当前里程碑边界”，不再用 Demo 同时表示三者。
- 参考 HolmesGPT 的 Toolset、调查循环和多数据源分层，但不照搬实现；HinataOps 继续强调 Evidence ID、原始
  Artifact 与上下文投影分离、细粒度读写策略、人工审批及执行后验证。
- 将原先永久化的“非目标”改为当前边界。目标架构允许 API/事件流、通用只读 Toolset、Runbook 和持久化，
  但具体技术与优先级必须在架构讨论和评测之后决定。
- 暂不在本条日志中写入 V3 详细方案或迁移任务，避免在关键边界尚未达成共识前固化设计。

### 结果

项目不再以“只完成 AoiLearn 演示”为成功标准，而以“用有限环境验证生产级通用架构的一组真实纵向切片”为
阶段目标。以后新增 AoiLearn 能力时，必须能够说明它验证了哪一项通用平台能力；纯粹针对单一故障文本的特判
不进入 Core。

### 验证与边界

本次首先修正文档定位，没有声称当前代码已经生产可用。讨论确认后，项目进一步形成
[V3 目标架构](ARCHITECTURE_V3.md)与[V3 迁移清单](V3_MIGRATION_CHECKLIST.md)，以可靠性、安全、可恢复性、
可观测性和真实评测作为最小可信切片的验收依据。
